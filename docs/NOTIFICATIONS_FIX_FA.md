# رفع باگ «اعلان‌ها در اپ نمایش داده نمی‌شوند» (۲۰۲۶-۱۰-۰۶)

## ۱) صورت مسئله

- وقتی کاربر در اپ **درخواست/گزارشی ثبت می‌کرد**، اعلانِ «ثبت درخواست» در
  فهرست اعلان‌های همان اپ دیده نمی‌شد.
- **ارسال اعلان از پنل ادمین** هم با خطا شکست می‌خورد (یا اعلان به فهرست اپ نمی‌رسید).
- فهرست اعلان‌ها برای همه‌ی کاربران **خالی** بود (بدون هیچ پیام خطایی در اپ).

## ۲) علت واقعی (با مدرک، از روی سرور زنده)

کاوش سرور زنده از GitHub Actions (ورک‌فلو **Diagnostics (live host)**، اسکریپت
`tools/diag/probe-notifications.sh`) این پاسخ‌ها را از `https://eplak.ir/eplak-fixed` گرفت:

| endpoint | پاسخ سرور زنده |
|---|---|
| `api/notifications.php` (همه‌ی حالت‌ها: با/بدون شماره، مهمان، read، delete) | `HTTP 500` — `{"success":false,"error":"SQLSTATE[42S22]: Column not found: 1054 Unknown column 'send_id' in 'SELECT'"}` |
| `api/news.php` | `HTTP 500` — `Unknown column 'badge' in 'SELECT'` |
| `api/ping.php`، `api/places.php`، `api/departments.php`، `api/push.php`، `admin/login.php` | `HTTP 200` (اتصال دیتابیس سالم است) |

یعنی **جدول‌های دیتابیسِ روی هاست از کد عقب‌تر بودند**: ستون‌های تازه‌ای که کد
استفاده می‌کند در دیتابیس وجود نداشتند:

- `notifications.send_id` → هم فهرست اعلان‌های اپ (`api/notifications.php`) و هم
  ارسال اعلان از پنل (`sendNotification()` در `admin/includes/functions.php`) با آن کار می‌کنند.
- `notifications.read_flag` → ثبت اعلان رویدادی (`shared/notify_events.php`).
- `news.badge` → `api/news.php`.
- `reports.client_ref` → فهرست گزارش‌ها.

### چرا خودکار ترمیم نمی‌شد؟

پروژه مکانیزم «همگام‌سازی خودکار اسکیما» دارد (`eplakRunSchemaSync()` که در
`eplakGetPdo()` صدا زده می‌شود)، اما اجرای آن به نشانه‌ی
`app_settings.schema_version` وابسته بود:

```php
return (string) eplakAppSetting($pdo, 'schema_version', '') !== EPLAK_SCHEMA_VERSION;
```

روی دیتابیسِ هاست، این نشانه **همان نسخه‌ی کد** ثبت شده بود، در حالی که ستون‌ها
واقعاً وجود نداشتند. پس هر درخواست «اسکیما به‌روز است» نتیجه می‌گرفت و همگام‌سازی
**هرگز اجرا نمی‌شد** — خطا دائمی می‌ماند.

دو حالت ممکن در دنیای واقعی:

| حالت | چه رخ می‌دهد | راه‌حل این نسخه |
|---|---|---|
| **الف)** نشانه‌ی نسخه به‌روز است ولی ستون‌ها نیستند | همگام‌سازی رد می‌شود → `Unknown column` → ۵۰۰ | بررسیِ ستون‌های حیاتی در هر درخواست + بالا بردن نسخه‌ی اسکیما → **ترمیم خودکار** |
| **ب)** کاربر دیتابیس اجازه‌ی `ALTER TABLE` ندارد | همگام‌سازی شکست می‌خورد و تا ۱۰ دقیقه تکرار نمی‌شود | پرس‌وجوها **بدون** آن ستون‌ها ساخته می‌شوند → هیچ ۵۰۰ و هیچ فهرست خالی‌ای رخ نمی‌دهد |

و یک باگ پنهانِ سوم: اپ فهرست اعلان‌ها را با `if (!res.ok) return false;` می‌گرفت؛
پاسخ ۵۰۰ **بی‌صدا** به «فهرست خالی» تبدیل می‌شد و هیچ‌کس نمی‌فهمید مشکل از سرور است.

## ۳) چه چیزهایی تغییر کرد

### سمت سرور (PHP) — بخش اصلیِ رفع باگ

| فایل | تغییر |
|---|---|
| `shared/bootstrap.php` | نسخه‌ی اسکیما به `2026-10-06.1` بالا رفت. `eplakSchemaSyncNeeded()` افزون بر نسخه، **ستون‌های حیاتی** را هم بررسی می‌کند (`eplakSchemaCriticalColumns()` / `eplakSchemaMissingColumns()`)؛ پس حتی با نشانه‌ی «به‌روز» هم ترمیم خودکار انجام می‌شود. کمک‌تابع‌های تازه: `eplakSelectColumns()` (ستونِ نبوده → `NULL`)، `eplakInsertRow()` (INSERT فقط با ستون‌های موجود)، `eplakIsSchemaError()` و `eplakSchemaErrorHint()`، و `eplakTableColumnCacheReset()` (تازه‌سازی حافظه‌ی ستون‌ها بعد از ALTER). |
| `api/notifications.php` | فهرست، «خوانده‌شده» و «حذف» همگی **بدون** `send_id`/`read_flag` هم کار می‌کنند. شماره‌ی کاربر با `eplakNotifyNormalizePhone()` یکسان می‌شود (`+98…`/`9…`/رقم فارسی → `09xxxxxxxxx`) تا اعلان‌ها با قالب دیگری که ذخیره شده‌اند گم نشوند. در صورت خطا، پاسخ علاوه بر `error` فیلدهای `schema`/`hint`/`missing` هم دارد. |
| `api/news.php` | ستون‌های نبوده (مثل `badge`) به‌صورت `NULL` انتخاب می‌شوند → دیگر ۵۰۰ نمی‌دهد. |
| `admin/includes/functions.php` | `sendNotification()` **خودش را ترمیم می‌کند**: اگر ستون `send_id` نباشد، یک‌بار همگام‌سازیِ اجباری اسکیما اجرا می‌شود (با رعایت مهلتِ ۱۰ دقیقه‌ایِ تلاشِ ناموفق) و اگر ترمیم ممکن نبود، اعلان «بدون» آن ستون نوشته می‌شود → ارسال از پنل دیگر با `Unknown column 'send_id' in 'INSERT INTO'` شکست نمی‌خورد. `getNotificationRecipients()` هم روی دیتابیس قدیمی فهرست خالی می‌دهد به‌جای خطا. |
| `admin/notifications.php` | اگر باز هم خطای اسکیمایی رخ دهد، پیامِ روی صفحه **علت و راه‌حل دقیق** را می‌نویسد (کدام ستون نیست، دکمه‌ی ترمیم کجاست، و دستور SQL جایگزین). |
| `shared/notify_events.php` | اعلانِ «ثبت درخواست» بدون `read_flag` هم ساخته می‌شود (پیش‌تر بی‌صدا از بین می‌رفت). |
| `shared/notification_reads.php` | به‌روزرسانی `read_flag` فقط وقتی آن ستون وجود داشته باشد. |
| `admin/version.php`، `admin/settings.php` | وضعیت «ستون‌های حیاتی دیتابیس» نمایش داده می‌شود (سالم / کدام ستون نیست) + راهنمای ترمیم. |

### سمت اپ (JS) — برای اینکه مشکل دیگر «بی‌صدا» نماند

| فایل | تغییر |
|---|---|
| `modules/live.js` | اگر سرور فهرست اعلان‌ها را با خطا بفرستد، علت (همان `hint`/`error` سرور) در **صفحه‌ی اعلان‌ها** با کادر قرمز نشان داده می‌شود؛ پیش‌تر فهرست فقط خالی می‌ماند. |
| `index.html` | کش‌باستر `modules/live.js?v=16`. |

| `tools/dev/tests/backend.test.mjs`، `push.test.mjs`، `app.test.mjs`، `geo.test.mjs` | بررسی «ستون‌های حیاتی» در صفحه‌ی بررسی نسخه، دکمه‌ی «ترمیم ساختار دیتابیس»، و مقاوم‌سازی مقایسه‌ی نسخه‌ی اسکیما. |

### اگر همین حالا خطا می‌گیرید (بدون آپلود)

خطای `⚠️ خطا در ارسال: SQLSTATE[42S22]: Column not found: 1054 Unknown column 'send_id' in 'INSERT INTO'`
یعنی کدِ روی هاست هنوز نسخه‌ی قدیمی است. سریع‌ترین راه‌ها:

1. **پنل ادمین → تنظیمات → «بررسی و ترمیم ساختار دیتابیس»** (۱۰ ثانیه، بدون آپلود).
2. اگر ترمیم ناموفق بود، در **phpMyAdmin** این سه خط اجرا شود (خطای
   `Duplicate column name` یعنی آن ستون از قبل هست؛ نادیده بگیرید):

```sql
ALTER TABLE `notifications` ADD COLUMN `send_id` INT NULL;
ALTER TABLE `notifications` ADD COLUMN `read_flag` TINYINT(1) DEFAULT 0;
ALTER TABLE `news`          ADD COLUMN `badge` VARCHAR(120) NULL;
```

3. برای بررسی اینکه چه ستون‌هایی کم است:

```sql
SHOW COLUMNS FROM `notifications`;
SHOW COLUMNS FROM `news`;
```

## ۴) روی هاست چه کار کنم؟

1. بسته‌ی به‌روزرسانی را روی هاست باز کنید (همان روش همیشگی: `docs/DEPLOY_UPDATE_FA.md`).
   فایل `shared/config.php` را **پوشش ندهید** (تنظیمات دیتابیس شماست).
2. هیچ کاری لازم نیست بکنید: اولین درخواست، ستون‌های نبوده را **خودکار** اضافه می‌کند
   (نسخه‌ی اسکیما بالا رفته + بررسی ستون‌های حیاتی).
3. اگر خواستید دستی مطمئن شوید: پنل ادمین → **تنظیمات** → دکمه‌ی
   **«بررسی و ترمیم ساختار دیتابیس»**. پیام «✅ ساختار دیتابیس ترمیم شد. ستون‌های
   اضافه‌شده: notifications.send_id …» را خواهید دید.
4. اگر پیام «⚠️ برخی ستون‌ها اضافه نشد» دیدید → کاربر دیتابیس اجازه‌ی
   `ALTER TABLE` ندارد: cPanel → *MySQL® Databases* → کاربرِ دیتابیس →
   **All Privileges**. (تا آن لحظه هم اپ کار می‌کند؛ فقط صفحه‌ی «گیرندگان اعلان»
   در پنل خالی می‌ماند.)
5. بررسی: پنل ادمین → **بررسی نسخه** → ردیف «ستون‌های حیاتی دیتابیس» باید «درست» باشد.

## ۵) چطور از بیرون تأیید کنم درست شده؟

- در گیت‌هاب: **Actions → Diagnostics (live host)** (با تغییر `tools/diag/**` خودکار اجرا
  می‌شود). بخش **داوری** باید سبز باشد و `api/notifications.php` و `api/news.php`
  کد `200` با `"success":true` بدهند. گزارش کامل در برچسب گیت `artifacts/diag`
  (مسیر `diag/diag-out/verdict.txt`) ذخیره می‌شود.
- یا از کامپیوتر خودتان:

```bash
bash tools/diag/probe-notifications.sh https://eplak.ir/eplak-fixed diag-out
```

- در اپ: صفحه‌ی اعلان‌ها را باز کنید؛ اگر سرور خطا بدهد حالا **علت** را می‌بینید
  (کادر قرمز) نه فهرست خالی.
